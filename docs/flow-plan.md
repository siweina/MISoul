# 先规划后执行

## 要解决的问题

小爱的界面自动化只有一个入口：

```
com.xiaomi.voiceassistant.UIAgentServiceForOSBot.controlApp(String query)
```

模型给它的是**一句话**，聊天里说的、定时任务到点跑的，都是这一句。问题在于这句话通常很笼统——「打开支付宝签到」。云端拿着这句话去界面上找，经常在首页找不到签到入口就放弃，或者乱点。

把这句话写成流程（「先点『我的』，再点『签到』」）就能走通。但让用户每次都背一遍按钮名字显然不现实，所以模块做了两件事：**先规划**、**再复用**。

## 机制

挂在 `controlApp` 上，只改交给执行方的那句文字，不代替用户点屏幕。

1. **先规划**（没有成功记录时）：笼统指令前面补一段通用规划要求——先按目标应用的实际界面想清楚要依次点哪些按钮、每个按钮的准确文字，再依次执行，找不到对应按钮就停下，不猜不乱点。这段话不含任何具体应用、具体按钮。
2. **再复用**（有成功记录时优先）：分步骤指令（两处以上「点击」）成功执行后，按「应用|末步目标|原文」记一条；下次同样应用、同样末步目标的笼统指令，直接改写成这条已验证的流程，不再重新规划。单步「只打开」不算成功，不记录。上限 50 条，同应用同目标覆盖旧的。

记录存在模块 App 的 `persona` prefs 里（`flow_store`），小爱进程通过 `PersonaProvider` 的 `flow_put` 方法回写。设置页「清除流程记录」清空它。

## 安全红线

命中这些词的指令**原样放行，绝不补全、绝不改写**：

```
支付 转账 付款 下单 购买 充值 提现 还款 汇款 付款码 信用卡 花呗 借呗
```

判断前先把应用名摘掉：

```
支付宝钱包 支付宝 微信支付 云闪付
```

1.0.4 的真实 bug 就在这：`query.contains("支付")` 会认为「打开支付宝签到」是支付动作，于是原样放行——结果所有支付宝相关的自动化都永远走不到规划分支，看起来就像「这个功能一开反而更坏了」。摘掉应用名之后，这句话里剩下「打开 签到」，不再命中。

## 与 MiAIPlus 共存

两者挂的是同一个方法。MiAIPlus 用 `beforeHookedMethod` + `setResult` 直接接管 `controlApp`，不调原方法——它自己那套控屏实现收到的参数，就是本模块改写后那一句，所以规划要求对两边都有效。真机日志里两个模块的 hook 依次装上，本模块在前：

```
[io.github.siweina.misoul,MISoul,...-2-11] hooking UIAgentServiceForOSBot.controlApp (先规划后执行)
[io.github.miaiplus,MiAIPlus,...-2-13] MiAIPlus: ready: ... + controlApp + ...
```

要注意的是**会话**而不是文字：两边同时要控屏时，后起来的那个会拿到「已有控屏会话」。同时开两个控屏类模块时，把其中一个的自动化能力关掉。

## 关掉与回退

- 开关默认关闭，独立于人格替换与定时任务放行
- 关掉后 `controlApp` 收到的就是模型原话，和小爱官方行为完全一致
- 应用改版导致旧流程失效：设置页清除记录，或关掉开关
